### 1.1 授权与已有改动

- 只实施用户授权的阶段和文件范围，阶段完成后汇报，未经授权不进入下一阶段。
- 开始修改前检查 `git status`、当前分支及已有补丁，保护用户的未提交和暂存内容。
- 新功能开发前执行 `git fetch origin master`，从最新 `origin/master` 创建中文功能分支，不在 `master` 上开发。连续阶段沿用已包含前序成果的授权开发分支，不能为了开始下一阶段丢弃前序工作。
- 只有明确获准后才执行 `git commit`、`git push`；不擅自合并、变基、强推、重置或清理已有改动。
- 临时文件放在 `/tmp/codex/`，项目正常产物和缓存保留原位置。
- 当前四文档修订任务不授权实现下面任何业务代码。

### 1.2 实施与验证方式

每阶段按“阅读已有代码 → 确定文件及职责 → 实现 → 相关测试 → 自查补丁 → 交付报告”执行。

- 使用既定技术栈和明确类型，不引入框架、ORM、外部队列或无实际职责的抽象。
- 目录只在需要时创建，以[架构模块定义](web-ssh-architecture-implementation-plan.md#modules)为准。
- 代码、配置、脚本和 SQL 的说明性注释使用中文，技术标识和工具指令保留原文。
- 格式化和自动修复仅作用于本阶段修改的文件，不运行会重写无关文件的批量修复。
- 依赖版本在初始化时固定；后续安装按现有锁文件进行，不借阶段实施升级依赖。
- 单元测试使用可控时钟和可控连接；涉及真实 SSH、浏览器和代理的结果单独记录，不能用替身测试代替集成验收。
- 验证后文件未再变化时，交付或获准提交前仅检查状态和补丁，不重复完整构建。

## 3. 第一阶段：项目基础设施

### 3.1 前提与依据

确认现有目录、工程、依赖锁文件和用户改动，已有可用基础应继续使用。

依据：[技术范围](web-ssh-design-development-plan.md)、[配置](web-ssh-design-development-plan.md#configuration)、[HTTP 通用契约](web-ssh-design-development-plan.md#api-common)、[数据库](web-ssh-design-development-plan.md#database)、[模块](web-ssh-architecture-implementation-plan.md#modules)、[存储运行规则](web-ssh-architecture-implementation-plan.md#storage-runtime)。

### 3.2 实施任务

1. 初始化 Go、Vue 3、TypeScript 和 Vite 工程，固定兼容的依赖版本；WebSocket 按[架构 §7.5](web-ssh-architecture-implementation-plan.md#ws-read-close)锁定 `github.com/coder/websocket v1.8.15`，HTTP 使用既定标准库方案。
2. 实现完整配置结构、默认值、严格解析和启动校验。所有参数名称、层级、单位、必填规则以核心配置表为准。
3. 选择并验证纯 Go SQLite 驱动，落实迁移版本记录及核心文档规定的全部表结构。后续阶段使用这些表，不临时另造认证或信任表。
4. 实现数据库连接初始化、短事务与关闭。逐物理连接应用并回读要求的 PRAGMA，连接重开仍须生效。
5. 建立统一 JSON 请求解析、响应和错误转换，按核心契约提供 `GET /api/health`。
6. 提供基础前端页面、API 错误展示和路由，开发使用 Vite，生产由 Go 嵌入的静态资源提供页面。
7. 建立 Dockerfile 多阶段构建骨架、配置及环境变量示例；不在此阶段伪称实际 Docker/NPM 部署通过。
8. 建立应用启动和退出入口，能够关闭本阶段 HTTP 与数据库资源，为后续资源登记提供明确接入点。

本阶段不建立真实 SSH Session，不实现登录业务或服务器管理页面。

### 3.3 必须验证

- 配置缺项使用定义的默认值；非法类型、范围、未知项和相关约束失败时阻止启动，错误说明可定位配置项。
- 数据库首次迁移、重复启动、迁移失败、不可写目录及连接重开行为正确。
- 在实际选定驱动上回读 PRAGMA，并通过非法外键写入和锁等待验证其效果；不能只检查配置文本。
- `.db` 及其 WAL 相关文件使用同一持久化目录，数据库访问失败不会被吞掉。
- 健康检查、静态页面、前端路由刷新及 API 路由互不冲突。
- 生产前端能够嵌入 Go，构建不依赖开发服务器。
- 关闭 HTTP/SQLite 后进程能够退出，无后台资源遗留。

### 3.4 完成条件

工程可构建、配置可校验、数据库初始化和重开行为已验证、HTTP 和嵌入页面可访问。交付实际命令和结果，以及选定 SQLite 驱动的初始化与备份能力依据。

## 4. 第二阶段：登录与服务器管理

### 4.1 前提与依据

阶段1完成。此阶段不创建长期 SSH Session。

依据：[认证](web-ssh-design-development-plan.md#authentication)、[认证 API](web-ssh-design-development-plan.md#api-auth)、[服务器 API](web-ssh-design-development-plan.md#api-servers)、[数据库](web-ssh-design-development-plan.md#database)、[Host Key 算法](web-ssh-architecture-implementation-plan.md#host-key)。

### 4.2 实施任务

1. 实现单管理员初始化、Argon2id 验证、Cookie 登录、到期和撤销，以及有界登录限流。
2. 实现同源与可信代理校验，明确开发访问和正式 HTTPS 的配置边界。
3. 实现 AES-256-GCM 密钥加载、随机 nonce、加解密和错误处理。查询 DTO 从类型上排除敏感数据。
4. 按核心契约实现服务器新增、查询、编辑、删除、分组、名称搜索及连接测试。
5. 建立服务器同步边界，协调配置快照、编辑、删除、Host Key 确认和后续 Session 名额预占。
6. 按架构实现 Host Key 探测记录、一次性 `probe_id`、内存 `config_version`、有界容量及到期清理。
7. 实现首次信任与公钥变化的人工确认交互；确认后的可信完整公钥按数据库契约持久化，未确认探测记录仅存内存。
8. 实现确认事务的确定回滚、不确定提交、重读失败和服务器不可用处理。提交结果不确定不能盲目重试旧探测。
9. 实现连接测试：身份验证通过后才进行 SSH 用户认证，完成后关闭临时连接，不创建 PTY、Shell 或可接管 Session。
10. 将探测和测试连接登记到应用资源管理中，超时或退出时可取消并回收。

### 4.3 必须验证

| 范围 | 场景与预期 |
|---|---|
| 登录 | 正确/错误密码、到期、退出、令牌撤销、限流及容量回收；未认证管理请求被拒绝 |
| Cookie 与来源 | 正式安全属性、开发配置边界、非法 Origin、非可信代理伪造请求头均符合契约 |
| 密码保存 | 加解密往返、nonce 不复用、错误密钥不覆盖旧数据、编辑未填密码保留密文 |
| 敏感信息 | API、日志和错误消息均无密码、密文、nonce、主密钥、令牌或完整 Host Key 泄漏 |
| 首次信任 | 探测到确认前不发送用户认证凭据、不持久化信任；拒绝确认不改变记录 |
| 公钥变化 | 展示当前目标的新旧指纹，未经确认不继续认证，确认后再次建连仍校验实际公钥 |
| 目标变化 | Host 或 Port 改变，即使公钥相同也重新确认；仅用户名/密码改变则保留信任但旧探测失效 |
| 凭证 | 伪造、过期、已用、异登录会话、异服务器、额外公钥字段和版本不符均拒绝 |
| 并发确认 | 同凭证只有一次成功；同服务器旧探测不能覆盖新信任；容量检查与插入不超限 |
| 并发编辑/删除 | 探测期间变更配置、改回原值、删除后重建，都不能接受旧结果 |
| 事务故障 | 确定回滚可在原期限内重试；不确定提交使旧版本失效并重读；重读失败拒绝继续使用旧快照 |
| 已信任测试 | 公钥匹配时直接完成受信任认证，不误签发确认凭证；测试使用同一版本的目标、用户名和认证材料快照 |
| 临时资源 | TCP/握手/认证阻塞、超时、用户取消及应用退出后，连接和协程均可回收 |

本阶段用受控替身验证“存在活动名额或正在创建时拒绝删除”的契约；认证中间件可单独验证 WS 升级前的拒绝逻辑。真正的 Session 删除竞争和 WebSocket 接入集成测试安排在阶段3，不得把本阶段替身结果记为那些集成测试已通过。

### 4.4 完成条件

登录、服务器管理、人工信任和测试连接闭环可用，Host Key 并发和事务失败测试通过；已确定后续建连使用的可信快照与同步边界。尚未实现真实终端和长期 Session，应在交付报告中明确。

## 5. 第三阶段：首条真实终端链路

### 5.1 前提与依据

阶段1–2完成，服务器已经能够提供受校验的连接配置和 Host Key 信任快照。

依据：[Session API](web-ssh-design-development-plan.md#api-sessions)、[所有权](web-ssh-architecture-implementation-plan.md#ownership)、[生命周期](web-ssh-architecture-implementation-plan.md#session-lifecycle)、[绑定](web-ssh-architecture-implementation-plan.md#binding)、[操作顺序](web-ssh-architecture-implementation-plan.md#operation-order)、[缓存](web-ssh-architecture-implementation-plan.md#output-buffer)、[协议](web-ssh-websocket-protocol.md)。

### 5.2 Session 与资源基础

1. 实现 Session Manager、每服务器名额、内存活动索引、连接快照和不可预测的 Session ID。
2. 实现创建、详情和关闭 API。创建前固定参数与信任快照并预占名额，网络操作在锁外进行。
3. 建连任务完成 SSH、PTY 和 Shell，Session 生命周期从应用派生，不依赖 HTTP 请求或 WebSocket。
4. 创建失败完整清理资源和名额；发布 Session 前检查应用停止状态，初始元数据写入失败不得发布。
5. Session 长期只保留非敏感连接快照和已建立资源，认证材料只由本次建连任务短暂使用。
6. 实现幂等统一关闭入口、基础离线计时和 SSH Keepalive；浏览器断开后持续读取 SSH，离线 Session 能按规则回收。
7. 接入阶段2的服务器删除保护，覆盖创建中、已连接、离线和关闭中的占用。
8. 提供最小手动关闭操作及确认；关闭本地标签不调用关闭 Session API。

### 5.3 首次凭证与 WebSocket

1. 实现 `POST /api/sessions/{id}/takeover` 的 `mode=attach` 分支，供首次绑定和后续恢复复用；此阶段不开放主动替换在线操作端。
2. 完成通用凭证记录、到期、容量、登录归属、目标和预期代次校验，以及提交时消费和其他凭证失效。
3. 实现原子首次绑定、当前 BrowserBinding 身份及立即失效机制。普通断开、登录撤销、写失败均撤销旧操作权。
4. 每条 WS 建立一个 Reader 和一个应用 Writer，业务协程经有界控制事件提交通知；输出按缓存游标读取，不建立无界输出数据队列。
5. 实现协议全部接入限制、消息顺序、心跳和统一通道关闭。登记全部已升级连接，包括未绑定及正在关闭的连接。
6. 输入和尺寸操作捕获所属 BrowserBinding，并在真正获准执行前校验有效性；已经失效的排队操作不能写 SSH。
7. WebSocket 失败仅解除浏览器绑定，SSH 故障通过 Session 统一关闭处理，两条健康检查链路独立。

### 5.4 缓存与前端最小闭环

1. 直接实现最终的双上限原始字节 OutputBuffer 和绝对偏移，不解码 UTF-8、不解析 ANSI、不调整原始字节。
2. 从 Shell 启动就读取和缓存输出，首次绑定可回放绑定前已产生的输出，不静默丢失提示符或 banner。
3. 按[发送顺序](web-ssh-websocket-protocol.md#output-order)实现一次稳定快照及连续实时输出；检测到无法连续读取时终止该浏览器通道。
4. 按[客户端 tracker](web-ssh-websocket-protocol.md#client-tracker)实现块偏移、单次在途 write、有界待写队列、回调确认和断线排空。
5. 实现首次绑定和已知 Session 的手动恢复。此阶段无需活动列表 UI，但必须复用最终凭证与协议，不能临时直连或以 Session ID 代替凭证。
6. 集成 xterm.js 输入、二进制输出、复制粘贴、尺寸同步和多标签；切换标签保留终端实例，关闭标签清理本地资源。
7. 截断提示显示在终端字节流之外；需要重建终端时按协议处理已提交写入、旧实例和偏移基线。
8. 客户端参数读取认证 API 的 `client_settings`，不能另写一组与服务端配置不同的限制。

### 5.5 必须验证

| 范围 | 场景与预期 |
|---|---|
| 真实链路 | 使用可控 SSH 环境执行普通命令、交互式程序、中文和 ANSI 输出，调整尺寸、多标签切换正常 |
| 创建 | 并发创建不突破名额；TCP/认证/PTY/Shell 失败释放资源；HTTP 响应丢失后仍可回收 |
| Host Key 集成 | 未信任不创建正式 Session；预占后发现公钥变化能释放名额并按原版本处理探测结果 |
| 服务器竞争 | 编辑与创建使用完整快照；删除与预占/关闭竞争不留下孤立活动 Session |
| 凭证 | 首次绑定有可调用的签发来源；非法、过期、重复使用或预期代次不符均拒绝；快照准备期间到期或被清理也不能提交 |
| 绑定失败 | 提交前失败不消耗仍有效凭证；提交后通知失败不恢复旧操作权；资源最终回收 |
| 普通断开 | 立即失效旧 Binding，排队未获准输入和 resize 被丢弃，延迟回调不能修改后续绑定 |
| 输出 | 首次绑定前输出可回放；正常字节精确保持；LF/CR/尾行及两个上限按架构工作 |
| 首次回放 | 绑定控制消息先于二进制输出；仅一次快照，后续缺口结束通道而 SSH 继续运行 |
| 前端偏移 | write 回调前不推进已处理偏移；同一实例顺序处理；队列有界；断线已提交写入完成后才能恢复 |
| 生命周期 | 离线计时、Keepalive、手动关闭和自然退出可用；重复关闭幂等，无自等待 |
| 协议接入 | 未登录/非法来源/绑定超时/非法消息/超限输入被拒绝，且不影响 SSH 生命周期 |
| 连接容量 | 并发 HTTP 升级不能突破预占上限；升级失败释放名额，关闭中的连接直到资源回收才归还名额 |
| 大粘贴 | 连续多个合法输入块按序转发，不因正常分块调度被误判为慢端；确实超过输入处理能力时有明确反馈且不自动补发 |
| 资源隔离 | 一个 Session 的慢写或浏览器失败不阻塞其他 Session、SSH 读取和缓存 |

使用 `go test -race ./...` 验证本阶段并发代码，真实 SSH 测试必须列出测试环境和实际结果。尚未实施自动恢复协调、主动接管 UI，不将手动恢复测试等同于它们已经完成。

#### 5.5.1 不完整帧头、正常空闲与资源回收专项验收

依据[架构 §7.5](web-ssh-architecture-implementation-plan.md#ws-read-close)，在阶段3的真实 HTTP/1.1 Upgrade 和 WS 生命周期上执行以下测试，不推迟到阶段7。测试客户端使用原始 TCP 编码帧，确认服务端已读到注入字节后再开始断言；可缩短配置时间并给出有限调度容差，但不能用 mock Reader 代替固定库，也不能只检查客户端已断开。

| 场景 | 必须断言 |
|---|---|
| 已绑定后半帧头停发 | 分别只发第一个基础字节、部分 16/64 位扩展长度、部分掩码；Reader 不返回消息读取器，消息计时器尚未启动，Writer 仍发出 Ping，Pong 期限到达后撤销 Binding 并进入统一终止；底层强关不超过 §7.5 的总预算与调度容差。 |
| Pong 不能越过半帧头 | 在未完成的 64 位长度字段后直接追加匹配 Ping 的原始 Pong 字节，明确这是故意构造的非法拼接；验证它们被当作当前帧头字节而非独立 Pong，不能让 Ping 成功或延长期限。 |
| 正常空闲与正常拆包 | 保持无应用输入超过多个 message_read_timeout 和至少六轮 Ping/Pong，连接和 Binding 仍有效；另测帧头正常分批到达并在相关期限内补全，可继续输入。不能以固定 Reader 读期限误杀空闲连接。 |
| 绑定前半帧头 | 升级后不发送数据或只发部分 bind 帧头，bind_timeout 从升级时生效，未绑定通道也完整回收。 |
| 心跳调度与写入阻塞 | 持续输出时到期 Ping 不被饿死；只读服务端数据而永不完成客户端帧头也不能保活。另让客户端不读以堵住应用 Write，按写入/关闭期限强关，Reader/Writer 均退出。 |
| Close 已经开始 | 让 Writer 卡在 Close 握手，并验证并发 CloseNow 不能代替强关；独立监督器关闭 ConnContext 中的底层连接后，Reader、Writer（含 Ping/Close）、执行器和监督器的完成信号全部到达，无自等待。 |
| 强关时 Ping 尚在等待 | 令 pong_timeout 大于 close_timeout，在 Ping 已发送后由另一终止原因触发关闭；终止同步取消在途 Ping context，不能因只关闭原始 socket 而让 Writer 等到原 Pong 期限，名额须在任务完成后回收。 |
| 名额与 SSH 隔离 | 将实际全局 WS 上限设为 1，关闭中仍拒绝额外升级，全部任务退出后只归还一次名额，新连接能立即升级并绑定；原 SSH 保持运行、输出继续进入缓存，重复终止不改变结果。 |

2026-11-14 设计复核证据：Go `1.26.5`、Linux/amd64（WSL2）、`coder/websocket v1.8.15`、真实环回 TCP/HTTP Upgrade、禁用压缩；临时实验位于 `/tmp/codex/ws-header-audit-20261114/`。在该目录执行 `./go/bin/go test -v -count=1 -timeout=30s .` 与 `./go/bin/go test -count=20 -timeout=45s .` 均通过。实验确认四类帧头阻塞；80ms Ping 超时后 Reader 仍阻塞，直接关闭底层连接才解除；追加 Pong 不能越过帧头；正常空闲六轮心跳及正常拆包通过；80ms bind 期限有效；60ms 关闭监督期限解除 Reader/Close/并发 CloseNow，模拟名额在任务完成后归零；堵塞的真实 TCP Write 与 Read 也均被解除；另确认原始 socket 关闭后在途 Ping 仍可等待，显式取消其 context 后即返回。测试源和日志分别为 `header_test.go`、`test-results.txt`、`repeat-results.txt`。

以上为固定库与最小回收模型的实测，未实现业务服务，不能代替上表的实际 Binding、名额管理器、SSH 隔离、持续输出调度和阶段并发验收。本机无 C 编译器，未运行 race；阶段3实际实现仍必须完成上述场景与 `go test -race ./...`。

### 5.6 完成条件

## 6. 第四阶段：Session 生命周期与输出缓存

### 6.1 前提与依据

阶段3已具备完整最小链路。本阶段基于同一 Session 和终端实例完善恢复与异常行为，不依赖阶段5的列表或主动接管功能。

依据：[生命周期](web-ssh-architecture-implementation-plan.md#session-lifecycle)、[缓存](web-ssh-architecture-implementation-plan.md#output-buffer)、[退出](web-ssh-architecture-implementation-plan.md#shutdown)、[tracker](web-ssh-websocket-protocol.md#client-tracker)、[恢复协调](web-ssh-websocket-protocol.md#reconnect)、[协议示例](web-ssh-websocket-protocol.md#examples)。

### 6.2 实施任务

1. 为保留的终端实例实现串行恢复协调器，统一网络断开、输出缺口和慢端触发的恢复入口。
2. 自动恢复只使用 `mode=attach` 和上次成功绑定代次；区分可有限重试的忙状态与必须停止的代次冲突。
3. 按配置限制重试次数、等待间隔和稳定连接判定，多次断线不能触发并发凭证请求或并发 WS。
4. 完善断线丢弃未提交队列、等待在途 write、排空超时销毁实例、新实例初始化和晚到回调隔离。
5. 完善截断时的终端重建、偏移基线及提示，让已处理画面、缓存起点和后续字节的关系符合协议。
6. 完善服务端慢写、输出缺口、控制队列满、消息超时和关闭握手阻塞的通道回收。
7. 完善离线超时竞争、SSH 操作超时、Keepalive 阻塞解除及运行元数据写入失败处理。
8. 完善统一退出：停止接入，取消建连/探测/测试，关闭已登记资源，在总期限内等待并强制解除残余阻塞。
9. 为资源限制、截止时间和关闭原因提供必要诊断，日志不记录凭证或终端内容。

### 6.3 缓存和终端专项测试

- 空缓存、单字节、单行、多 LF、CR、跨读取 CRLF、尾部未换行以及两个上限分别或同时触发。
- 无换行长输出仍有界；多次淘汰后绝对偏移不重新编号，安全整数边界不会回绕。
- UTF-8 和 ANSI 跨任意读取/消息边界时原始字节保持；缓存起点截入序列时不发生服务器清洗或补字节。
- 连续输出未丢失的客户端不因服务端淘汰已处理历史而收到截断提示。
- 稳定快照复制后缓存淘汰不修改该快照；回放后的游标落到缓存之前时结束当前通道。
- 在历史回放中断、首块前断开、实时块传输后断开等位置恢复，只从当前实例连续完成的偏移请求。
- 人为延迟 write 回调时，已收到但未提交数据可被丢弃，在途数据完成后不被重复回放。
- write 排空超时后旧实例被销毁，旧回调不推进新实例偏移，新实例按协议重新初始化。
- 发生截断时重建终端，清理旧解析器和画面；提示承认保留后缀无法完整恢复历史终端状态。
- 较小缓存配合持续高输出和慢浏览器反复制造缺口，验证自动恢复有次数上限、队列有界，最终可由用户主动重试。

### 6.4 生命周期与协议故障测试

| 范围 | 场景与预期 |
|---|---|
| 恢复竞争 | 多个断线事件、用户关闭视图、登录撤销与重试同时发生，不产生多条恢复链 |
| 重试预算 | 稳定资格只能消费一次；后续连续 HTTP 凭证失败不能反复重置次数，绑定后立即缺口也不能获得新预算 |
| 视图销毁 | 并发 stop/dispose、排空超时、write 异常与迟到回调按协议回收；销毁期间不创建替代终端，不再联网 |
| 代次保护 | 旧连接仍在但代次未变时有限等待；代次变化立即停止，自动恢复不抢回其他设备操作权 |
| 离线回收 | 使用可控时钟验证期限；重新绑定后旧超时任务不能关闭当前 Session |
| SSH Keepalive | 拒绝回复仍算有响应；连续超时只保留一个在途探测；关闭后解除阻塞并回收协程 |
| Reader | 分片累计上限、不完整消息、读取器返回前等待和整条消息期限均按固定依赖实际验证；复用[阶段3帧头专项验收](#ws-header-acceptance)，加入连续 100 轮连接/阻塞/关闭及与应用退出的竞争，确认任务、定时器和全局名额恢复基线 |
| Writer | 控制与输出顺序、终止事件中断回放、写失败、队列满和关闭预算均无并发写或无限等待 |
| 心跳 | 浏览器无输入仍可保持，Ping/Pong 失联只关闭通道，SSH Keepalive 状态独立 |
| 统一关闭 | 手动、自然退出、Keepalive 和超时同时发生只关闭一次，工作协程不等待自身；CLOSING/CLOSED 后迟到的 Detach 或 Reader/Writer 回调不能回退状态或重设离线期限 |
| 运行元数据 | 写入失败不回滚实际连接状态、不形成重试积压；最终关闭快照使用独立清理上下文，旧状态不能覆盖最终状态；启动清理失败不开放服务 |
| 应用退出 | 创建、探测、测试、绑定及关闭中收到停止信号，均不再发布新资源并在总期限内结束 |
| 硬截止 | 阻塞的 SSH/WS/HTTP 底层连接可被关闭，通知送达不是清理完成的前置条件 |

### 6.5 完成条件

同实例自动恢复、缺口处理、慢端和退出路径通过测试；明确哪类错误停止恢复、哪类允许有限重试。证明内存、队列、协程和重试均有边界。阶段3建立的 API、协议和缓存规则保持一致。

## 7. 第五阶段：会话管理与跨设备接管

### 7.1 前提与依据

阶段3的凭证和原子绑定、阶段4的恢复与资源处理已经完成。本阶段新增用户主动替换操作端的业务，不重新设计通用凭证或回放机制。

依据：[Session API](web-ssh-design-development-plan.md#api-sessions)、[绑定](web-ssh-architecture-implementation-plan.md#binding)、[操作串行规则](web-ssh-architecture-implementation-plan.md#operation-order)、[绑定协议](web-ssh-websocket-protocol.md#bind)、[消息](web-ssh-websocket-protocol.md#messages)。

### 7.2 实施任务

1. 实现活动会话列表 API，与阶段3的详情和关闭接口一起构成完整会话管理。
2. 活动状态从 Session Manager 查询；数据库历史元数据不伪造成可接管会话。已移除会话的详情和幂等关闭行为沿用核心契约。
3. 实现独立于本地终端标签的会话列表，展示连接目标快照、状态、时间及剩余保留时间。
4. 扩展 `POST /api/sessions/{id}/takeover` 的 `mode=takeover`，供用户主动打开或接管 CONNECTED、DISCONNECTED Session。
5. 复用现有凭证与 WS 提交机制。HTTP 准备只签发凭证，只有新 WS 提交成功才替换当前绑定。
6. 完善接管与在途输入/resize 的串行控制、等待超时及旧 Binding 失效；提交失败保留当前操作端。
7. 新端按协议建立终端，旧端收到接管结果后停止输入与自动恢复；通知失败时也不能依赖旧端自觉停止来保证权限。
8. 页面刷新和新设备新建终端实例，从该实例自己的起点恢复，不能沿用旧设备偏移。
9. 同一浏览器已有标签时优先定位该标签；用户关闭远端 Session 必须执行独立明确操作并确认。

### 7.3 必须验证

- CONNECTED、DISCONNECTED 可主动接管，CONNECTING、CLOSING 和已关闭状态不能提交绑定。
- 凭证签发后新设备未连接、绑定超时、非法偏移、过期和权限失败均不替换旧端。
- 两个请求可针对同一代次取得凭证，但只有一个 WS 提交成功，另一个收到冲突。
- 同凭证并发提交、不同凭证同代次竞争和登录撤销竞争均只有有效结果。
- 接管等待在途 SSH 操作超时不提交替换；已发送输入不可撤回，排队未获准旧操作不再执行。
- 新端提交后发送成功通知失败，旧绑定也不恢复；后续使用当前状态进行恢复或主动操作。
- 旧输入、旧 resize、旧断开及旧输出任务不能影响新 Binding。
- 旧端没收到接管通知就断线时，自动 attach 因代次变化停止，不自动夺回会话。
- 接管与离线超时、手动关闭、SSH 自然退出及应用停止同时发生，操作权与资源回收一致。
- 接管时持续输出、回放后缺口、慢新端仍使用既有单次回放和有限恢复规则。
- 已有 Session 的 SSH Connection 和 Shell 不被重建，远端命令不会因浏览器替换被主动终止。
- 页面刷新和跨设备恢复按新实例处理；同实例恢复保留连续处理完成的偏移。
- 会话列表来自内存事实，关闭后的查询与幂等删除符合核心 API；服务器编辑不改变既有会话的连接目标显示。

### 7.4 完成条件

可从另一设备打开或接管已有会话，同代次竞争仅一个提交成功，旧端不能继续操作或自动抢回。列表和终端标签职责分离，HTTP 准备、WS 提交、通知失败和资源清理均有实测结果。

- 关闭标签仅销毁本地视图；关闭远端 Session 必须确认，结果与列表及时一致。
- Host Key 首次/变更/目标变化提示完整，取消和凭证过期不误写信任。
- 密码/私钥两种认证方式可分别完成保存、测试和真实 SSH 终端；文件格式、口令、大小、multipart、并发、解析资源限制及失败保留旧凭据符合 AK 验收。
- 私钥原始字节上传/落盘/读取/恢复前后完全一致；Passphrase 只写、独立加密、不回传/记录。
- 私钥文件缺失/损坏仅影响关联服务器；数据库 Passphrase 解密失败按启动策略阻止启动；存储卷故障暂停 GC。
- 容器重建后独立私钥卷、UID/GID 10001:10001 和目录/文件权限正确；受控停机备份包含一致数据库、对应私钥对象、清单/校验、匹配主密钥及版本信息，且记录备份会终止 SSH Session。
- 孤儿回收采用启动对账+运行周期扫描+正常操作登记候选，默认 24 小时宽限；每 10 分钟扫描，每轮最多检查 100 个、删除 20 个、1 秒软预算，并完整保护引用、租约、事务和备份。
- 被接管和恢复次数用尽后，界面提供明确状态和主动操作，不能后台持续抢回。
- 历史截断提示独立于字节流，终端重建的画面变化与状态一致。
- 多次打开关闭标签和页面不遗留 xterm 实例、监听器、WS 或恢复任务。
- 不出现页面横向溢出，必要错误按具体操作显示，不增加常驻说明占用终端空间。

### 8.4 完成条件

桌面与移动端均能完成登录、服务器管理、终端操作、恢复、接管和关闭；新增密码与私钥认证均完成后端 AK 与真实设备 M16 验收。6-K.3 完成后端集成/持久化验证，6-3 完成认证 UI 联调，6-6 完成真实设备文件选择链路，方可将认证能力记为第六阶段交付。交付实际浏览器/设备覆盖及未验证环境，不将桌面缩放截图当作真实手机操作验收。

## 9. 第七阶段：稳定性测试与交付

### 9.1 前提与依据

阶段1–6完成。本阶段修复发现的问题、完成回归和交付，不扩充第一版产品范围。

依据：[产品验收](web-ssh-design-development-plan.md#acceptance)、[架构退出](web-ssh-architecture-implementation-plan.md#shutdown)、[存储运行规则](web-ssh-architecture-implementation-plan.md#storage-runtime)、[协议限制](web-ssh-websocket-protocol.md#limits)及下方追踪矩阵。

### 9.2 全面验证

1. 运行 Go 静态检查、构建及 race 测试，检查真实输出而不只记录退出码；前端执行现有脚本定义的类型检查和构建。
2. 重复创建、断开、恢复、接管和关闭，观察连接、goroutine、内存和队列是否回到合理基线。
3. 回归阶段2–5的重要并发组合，加入停止信号、数据库忙/失败、网络阻塞和输出洪流。
4. 验证启动清理历史活动记录，进程或容器重启后旧 Session、缓存和一次性凭证均不能恢复。
5. 使用已固定版本验证 WebSocket Reader、Ping/Pong、Close 和底层强制关闭的真实行为，不能只凭伪代码或库文档假定。
6. 验证 SQLite 连接重开及 WAL 已提交数据的正常持久化；私钥认证启用后的完整恢复集按受控停机流程验证，必须包含一致数据库、对应私钥对象、清单/完整性校验、匹配主密钥独立保管信息及程序/数据结构版本。SQLite `VACUUM INTO` 的单库一致性不能替代数据库与私钥目录的完整恢复集。
7. 检查 API 字段、错误码、敏感信息、权限、Origin、容量、整数范围和配置联动均符合权威文档。
8. 检查端到端输出无静默跳过：连续流保持有序；有缺口时明确结束通道并按恢复规则处理。

### 9.3 部署材料

交付 Dockerfile、Compose、配置示例、环境变量示例和部署说明，并验证示例与核心配置定义一致。

- 使用 Node 构建前端、Go 嵌入并编译、最终单容器运行的既定方式。
- SQLite 数据目录整体持久化；配置只读挂载；加密主密钥独立注入，不写入镜像。
- 容器将停止信号传递给 Go 主进程；Compose 停止宽限期大于应用总退出期限。
- NPM 文档说明 HTTPS、WebSocket 支持、代理目标、超时、可信来源和 Cookie 配置。
- 首版备份只定义受控停机备份：停止服务访问和进程、关闭数据库后，复制一致 SQLite 数据库及其引用的私钥对象，附清单/完整性校验、匹配主密钥独立保管信息和程序/数据结构版本；备份会终止现有 SSH Session。首版不宣称支持在线 DB+文件一致性备份，不只复制运行中的 `.db`。
- 私钥卷独立挂载到 `/var/lib/web-ssh/ssh-keys/`，宿主目录需预建并配置 UID/GID 10001:10001、目录 0700/文件 0600；容器重建后验证原始文件持续存在。
- 正式镜像构建、部署和远程环境验收按既定范围交给 ops；本地代码验证与 ops 验收分别记录。
- 未执行的 Docker、NPM、移动设备或真实 SSH 场景保留“待验”，不填写为通过。

### 9.4 完成条件

已授权范围内的实际检查完成、阻止交付的问题修复、产品验收逐项有证据。环境尚未具备的验收单独列出对象、所需操作和负责人，不以“代码构建成功”替代运行环境验收。

### 10.2 验证命令与范围

在实际 Go 模块目录执行适用检查；涉及并发的阶段必须包含 race 检查：

```bash
go vet ./...
go test ./...
go test -race ./...
go build ./...
```

`gofmt` 仅针对本阶段修改的 Go 文件执行。前端先读取 `package.json`，使用实际存在的类型检查、测试和构建脚本，不虚构 `npm run` 命令。集成测试注明使用的 SSH 服务、数据库、浏览器和代理；模拟故障与真实环境结果分开记录。
